# GitLab MR Code Review

對指定的 GitLab MR 進行 code review。

**參數：** "$ARGUMENTS"（MR number）　**全域鐵則：所有輸出使用中文。**

## 核心原則

**開始前先用 Skill 工具載入 `alma:principles`**（寫與審共用的工程原則）。以下引用都用它的條目標題，例如〈先找現成的〉。本段只放 review 專屬的姿態。

**不要當 yes-man reviewer。** 你的價值在找出作者沒看到的問題，不是確認程式碼能跑。

- 邏輯正確不代表做法合理——主動站對立面問「有沒有更好的做法？業界常見做法？這設計有什麼隱患？」
- 即使只是建議（不強制改）也要明確指出，別輕描淡寫帶過。
- 有現成工具不用、過度設計、名實不符，分別照〈先找現成的〉〈只為真實的使用者抽象（YAGNI）〉〈評它做什麼，不是它宣稱什麼〉的「審」做。

**對稱面：別把既有慣例當成本 MR 的問題。** 列 finding 前先驗證它是**本 MR 引入的**、還是**codebase 早就成立的系統級不變式**——去看 sibling code（同類模組、既有同型操作）有沒有一樣的假設。
- 判準：若這假設被打破時其他既有程式碼會**先**出事、後果相當或更嚴重，那是專案級架構議題、非本 MR scope。
- **但「非本 MR scope」≠「silently drop」。** 真的既有債（已驗證、值得一張票）仍可寫進 comment，但**必須明講「與本 MR 無關，建議另開案」**，把開票決定交還使用者，別自己丟掉。**防呆**：只有驗證過、值得一張票才這樣附；別每個 tangent 都貼「另案」變雜訊，也別把沒驗證的臆測丟給使用者背。
- 提出前先 grep 同型 pattern／讀啟動流程查一下，成本低、避免被打臉。（例：某並發保護只用行程內鎖，但整個 app 排程層本就假設單一實例運行，這是專案級不變式、非本 MR 該補）

**YAGNI 在 review 互動中的兩條。**
- **可以討論，但要使用者開口**：使用者主動想深入替代設計就陪他展開，但心裡清楚這是**探索**、不自動變 finding／寫進 comment。
- **最重要用途：當面點出「使用者自己」在過度設計。** 使用者本人在討論裡替想像需求補抽象（繼承、工廠、參數化…）時，當場直說「這是 YAGNI」，別順著一起蓋——陪他展開 ≠ 同意他的方向。

## 回應格式

Phase 2 設計討論、Phase 3 摘要、Phase 4 解說、Phase 5 comment **都適用這一套**。

**送出任何回應前，逐項勾，全部勾完才送**（漏勾＝重寫；這是動作、不是原則，最常整組漏掉）：

- [ ] **① 第一句白話結論** —— 一句話講「會發生什麼壞事／這段在做什麼」。
  **白話的定義 = 一個從沒開過這個 repo 的人，每個字都懂。** 三條硬標準：
  1. **結論裡不出現程式的專有名詞**——方法名（sync_batch_status）、欄位/變數名（rowcount、updated_at、status）、這個 repo 自創的縮寫或暱稱（guard、兩叉/三叉）。一律用它的「角色/作用」代替：不是「sync_batch_status」，是「負責算出整批整體狀態的共用函式」；不是「guard」，是「守門條件」。
  2. **講「壞了什麼、對誰有什麼影響」，不是「機制怎麼運作」**：不是「rowcount 誤回 1」，是「多發一則假通知」。
  3. **檔名、行號、SQL、方法名只准出現在底下「怎麼改／位置」段落，結論一個都不放**（位置歸 ③）。
  - 自我測試：把結論唸給沒看過這份 code 的人，只要有一個字他得停下來問「那是什麼」，就是沒過、重寫。
  - 對照範例——太術語 ✗：「共用的 sync SQL 被迫把 guard 從 running 放寬到含 failed，踩醒 updated_at 讓 rowcount 誤回 1 的老地雷」；白話 ✓：「有個共用函式負責看子項目算出整體狀態，這次放寬了它一個守門條件，害它每清一條就多發一則假通知」。
  - **一條要修的 finding／定案，結論拆成兩塊、別揉成一段**：先一段「發生了什麼問題」（只講症狀＋為何是問題，不摻怎麼修），再一段「建議怎麼做」。反射毛病是把問題＋根因＋修法全塞進同一段，讀者得自己拆——先問題、後建議，兩塊分開寫。（純確認／單行回覆走 ⑥ 豁免，不用硬拆）
- [ ] **② 補地基一句** —— 讀者不懂該子系統時，開頭先補**一句**「本來怎麼運作」再講 bug。順序：規則（本來怎樣）→ bug（哪裡壞）→ 具體例子走到底 →（需要才補）後果對誰造成什麼。**是一句不是一段**，對方本來就熟的機制別硬塞。
- [ ] **③ 位置即解釋** —— 每點條列 `檔案:行:方法`，直接說這行在 bug／流程裡扮演什麼角色。**不要**先寫一整段抽象術語、再另附一個乾巴巴的位置清單——那是把拼因果丟給讀者。
- [ ] **④ 判斷分三層** —— 一定要提（正確性風險、明顯遺漏、做法明顯不合理）／值得討論但不擋 merge（影響有限）／選擇不提（記原因、不發布，如既有架構債、作者已知 TODO、量級不構成問題）。前兩層合併為第一版 review 清單。
- [ ] **⑤ 沒有版面噪音** —— 不貼「白話／術語補充」這種欄位標題、不把三句能講完的結論埋進表格或多層子句。
- [ ] **⑥ 輕量豁免** —— 單行事實、短回覆、純確認不硬套上面；Phase 2 的目標陳述不用套 ①③。

（需要時才補：對照——為什麼別的路徑沒事。）

## 流程

### Phase 1: 取得 MR 資訊與需求

1. 從環境變數取得 GitLab URL (`GITLAB_URL`) 與 Project ID (`GITLAB_PROJECT_ID`)（沒設就查 Claude Code 的專案 auto-memory `MEMORY.md`；都沒有就問使用者，別猜），透過 GitLab API 用 MR number 查出 source branch 與 `diff_refs`（`base_sha`、`head_sha`）。
2. `git fetch origin` 確保最新。
3. **切換到 MR 的 source branch**（`git checkout`／`git switch <source_branch>`）：讓後續 `Read`／`grep -n` 直接對到真實檔案與**真實行號**，不必逐檔 `git show origin/<branch>:<file>`。
   - **防呆**：切換前先看 `git status`，只有**已追蹤檔的未提交修改**（會被 checkout 覆蓋／衝突的那種）才**先提醒使用者、別硬切**；純 untracked 檔（如 `??` 新目錄）不擋 checkout，放行即可。
   - checkout 後仍用 `base_sha..head_sha` 界定 diff 範圍（分支 HEAD 不影響 diff 範圍的正確性）；review 完不必主動切回原分支，除非使用者要求。
4. 用 `base_sha..head_sha` 界定範圍（**不要用 `origin/main...origin/<branch>`，main 可能已前進、會混入不屬於此 MR 的變更**）：這一步只看 `git log --oneline`、`git diff --stat`，完整 `git diff` 留到讀完需求之後（Phase 2）。
5. **先讀需求，寫出目標**：review 要從需求推，不能從實作反推——拿程式碼跟它自己比，只查得出內部矛盾，查不出「有沒有做到該做的事」，跟照實作寫測試是同一個毛病。
   - 讀 Jira 的**本單、父單、前置／後續子單**，只抽「要做什麼」：目標、人做的決定、驗收條件、已接受的風險。目標常不只一個，漏一個，後面的判斷會整組偏掉。
   - **分辨來源**：人做的決定（標「user 決定」、會議紀錄、需求方原話）才是需求。AI 寫的推論、理由、架構屬於「怎麼做」：看到了也先不採信，跟作者的 Decisions & Tradeoffs 一樣，等 Phase 2 建完模型再回頭當假設對帳。訊號：卡片建立時間晚於分支第一個 commit＝回頭補的卡；段落結構像 MR 描述＝多半從程式碼產生。判斷不了就標信心，不硬判。
   - **MR 描述**：「程式碼做了什麼」的段落不當量尺，但可拿來對帳——它宣稱的行為跟程式碼不一致處就是 finding 線索。「為什麼、否決過什麼、接受了哪些風險」才有參考價值。
   - **沒有卡、卡很空、或 Jira 連不上**：從觸發事件（事故、前置單、review 討論）、commit message、MR 標題推目標，並明講「沒有需求來源，目標是推測」。
   - **目標本身也可以質疑**：可能在修症狀不是根因、目標之間互斥、或漏了顯然該顧的面向（如資安）。質疑目標也是 Phase 2 的產出。

### Phase 2: 目標與設計（先討論設計合不合理，再看 bug）

設計要改的話，行號級問題多半跟著消失；先倒一長串 bug，也會把使用者帶去逐條看清單，而不是從「這樣設計對不對」想起。

**適用範圍**：讀完 diff 後問「有沒有新增元件，或改變了某段流程的行為／步驟順序（含並發、狀態轉換、排程互動）」——有就獨立走 Phase 2；沒有（多數 bug fix、純重構、小修改），Phase 2 和 Phase 3 合成一則送出：一句目標＋程式碼層判斷。

1. **建模型，順序防錨定**：需求（Phase 1 第 5 步，量尺）→ 讀完整 `git diff`，並追到足以畫完流程圖的上下文與呼叫鏈，自己寫下「這個設計怎麼服務目標＋哪裡可能爆」的假設 → **然後**才讀作者的 Decisions & Tradeoffs 與 Jira 裡 AI 寫的架構理由對帳。先讀作者框架會被他鋪的線帶著走。
   - **Decisions & Tradeoffs 仍要讀，只是往後放**：作者可能已考慮並否決某些替代方案（如為配合同表／同模組既有慣例而選了看似次優的做法），提建議要回應他的理由、別重提被否決的方案。
   - **對帳要雙向**：他的情境有沒有你沒算到的？你的假設有沒有戳破他沒算到的？（例：作者宣稱某動作「不會觸發通知」，自己追一遍才發現無實質狀態變更也會觸發。）
2. **量目標**：做到了哪些、離目標還差什麼、有沒有被已排程的後續卡解決。
3. **設計合不合理**（判斷依據優先是目標，不是程式碼本身）：
   - [ ] **每個設計選擇／參數的理由，對應哪個目標？那個理由在這個設計下還成立嗎？** 對不上就是在優化卡片沒要的指標。（例：參數依「吞吐量」調，但目標是可靠送達）
   - [ ] **真正的限制在哪一層？設計的單位跟它一致嗎？**（適用並發、限流、資源類設計）
   - [ ] **目標之間有衝突時怎麼取捨？為了目標該做的事做了沒？**
   - **設計 vs bug 的分界**：不改設計也能修好的是 bug（歸 Phase 3）；要改設計才修得好的是設計問題（歸這裡）。
   - 產出是「哪裡不合理、對應哪個目標」，**最多附一句方向**（同 YAGNI）；完整替代設計等使用者開口才展開。
4. **交付內容（要短）**：
   - **我理解的目標＋依據**：一句話寫出目標（有兩個就都寫），註明從哪裡來（哪張卡哪段、人做的決定或 AI 寫的、或推測）。**不擋流程**：使用者沒糾正就照它繼續；只有目標是推測、或卡片是 AI 產的時，才明確請使用者確認。使用者修正了目標，第 2、3 步要重做。
   - **改動的是一段流程就畫文字流程圖**：只畫設計，含改前與改後（新增的流程只畫改後）、主要路徑、錯誤路徑。畫圖也是逼自己把每條路徑追完的檢查。使用者要求時才換成網頁版（Artifact）。
   - 第 2、3 步看到的不合理處、要問作者的地方，每點一兩句，依回應格式寫。完整盤點不放這裡。
   - **嚴重 bug 例外**：建模時撞到「一定要提」等級的問題（正確性風險、資料遺失、資安），用一句話先標出來，細節留 Phase 3——流程不能壓下嚴重問題。
5. **停在這裡，跟使用者討論設計。** 角色定位同 Phase 4：保持中立、每個觀點獨立判斷、不連鎖同意。
   - **方向要作者回答時**：可先發一則「對齊方向」的 comment 給作者（走 Phase 5 的發布流程），寫明不同答案各自決定接下來往哪看，不標擋不擋；等作者回答再進 Phase 3。

**設計討論有結論之前（設計沒問題，或要改的方向已經講清楚），不進入 Phase 3。**

### Phase 3: 程式碼

Phase 2 已讀過完整 diff 和主要呼叫鏈，這裡補追沒追到的路徑並做判斷，不從頭重讀。

- **設計要大改時**：先不逐行挑。作者決定維持原設計，再補完整的逐行檢查；在專案 MEMORY 記一筆「等作者回覆設計，維持原設計就補逐行」，防止跨 session 忘記。

1. **補讀 Phase 2 沒追到的**：修改既有程式碼的上下文、其餘呼叫鏈與影響範圍。
2. **判斷先行**：第一個區塊是程式碼層判斷（依回應格式寫），最重要的 findings 放**最上面**。
   - 先看正確性：邏輯（上下游是否仍正確、有沒有破壞既有流程）、錯誤處理（是否用例外控制流程、有無錯誤恢復）、並發（race condition、要不要鎖）。
   - 正確性要特別對的兩條：新加的 guard、重試、吞例外 → 〈修在產生錯誤狀態的地方〉；狀態由子項目聚合 → 〈狀態由別處推導時，先列推導表〉。
   - 再**逐項勾（沒找到 bug ≠ 好）**——「實作乾淨／可以合」的實際意思只是「沒找到 bug」，正確性是最低門檻。每項照原則檔該條的「審」做：
     - [ ] **做法**：〈先找現成的〉〈只為真實的使用者抽象（YAGNI）〉；另看職責放對層了嗎？跟既有慣例一致嗎？綁死特定值，還是依意圖判斷？
     - [ ] **複雜度與維護成本**：〈複雜度跟問題相稱〉
     - [ ] **出事看得到嗎**：〈出事要看得到〉
     - [ ] **測試**：〈好的測試〉
   - 開場寫**具體判斷**（例：「沒有 bug，但隊伍滿時靜默阻塞、測試偏重」），**禁止用通用稱讚**（「實作乾淨」「這張很好」）當開頭。都沒問題時，逐項各寫一句看了什麼，不能只寫「已檢查」。
3. 判斷之後才附完整盤點當佐證（可長，但在判斷底下）：背景與目的、核心設計決策、影響流程盤點（先描述被改動的既有流程**原本在做什麼**、走完整遍，再說明本 MR 的調整＋檔案路徑行號）、各檔案角色與變更內容。**略過純格式化變更**（ruff 排版、import 排序、引號風格）。Phase 2 畫過流程圖的，把 finding 用 ①② 標在圖上對應的那一格。

**使用者看過程式碼層判斷之前，不進入 Phase 4。**

### Phase 4: 互動式 Review

進入互動模式，等使用者指出他關注的區段或提出觀點。

**角色定位：**
- 保持中立，不預設使用者一定正確；判斷有誤或過度解讀就直接指出。
- 使用者提觀點 → 先獨立判斷是否合理、再從正反兩面分析；成立就補「對方可能怎麼反駁＋你怎麼回應」，不成立就說明原因。
- 使用者問「你覺得呢」→ 給分析和建議；選程式碼問「這在幹嘛」→ 具體解釋（帶入實際的變數名、方法名、資料流）、不急著評價；說「加上」→ 記錄到 review 清單。

**常見偏差（必須警惕）——「不當 yes-man」在互動中的具體形式：**
- **跟著使用者的節奏 ≠ 同意使用者。** 跟節奏是回應他關注的方向，不是跟他的立場。第一反應該是「這觀點對不對？有什麼 trade-off？」而不是「怎麼把它寫進 comment」——好觀點也有 trade-off。
- **警惕連鎖同意。** 同意第一個觀點後，後續基於它的推論會慣性跟著同意；每個觀點都要獨立判斷。

**不要主動倒出所有建議。** 跟著使用者的節奏走，他問什麼答什麼，他提什麼就幫他完善。

### Phase 5: 發布 Review

當使用者要求發布時：

1. 整理所有 review points，每點含：標題、位置（檔案:行號）、說明。用 markdown 格式。
2. **發布前對抗檢查**：有「一定要提」等級的點才開；只有「不擋 merge」的點時，問使用者要不要開。
   - 開一個新的 subagent，給它 comment 本文、MR 編號、diff 範圍、Phase 2 的目標陳述與依據、MR 描述裡作者寫的取捨原文；**不給我們的對話**。
   - 它做三件事：①**反駁每一點**（回程式碼驗證機制和行號，試著證明不成立或講過頭）②**測可讀性**（作者只讀第一句，知道要改什麼嗎？）③**順帶發現的新問題**（只列事實與證據）。各點嚴重度不由它重評，新問題的分級由我做。
   - 某一點是推翻作者設計、要求大改這種等級的主張時，改開兩個不同 model（例：Fable＋Sonnet）。
   - **新冒出來的問題要分級**：「一定要提」那層的，我先自己回程式碼驗證成立，才併進這次 comment，並跟使用者講清楚是這一步新抓到的；不到這個等級的另外列給使用者，不擋發布。不讓小問題一路延伸，也不讓嚴重問題被流程壓下來。
   - 對帳時每條都自己回程式碼驗證，不照講得最篤定的那份走。
3. 連同對抗檢查的結果（哪幾點被修正、新抓到什麼）一起顯示給使用者確認。
4. 使用者確認後，**發布前逐項勾，全部勾完才發**：

   - [ ] **使用者觀點驗證**：Phase 2～4 提的觀點對照程式碼是否成立？有誤主動指出。
   - [ ] **語氣**：專業中立，別太強硬或帶指責。
   - [ ] **依回應格式寫**：comment 是給作者照著改的產出物，不是分析稿——他掃第一句就該知道要做什麼。
   - [ ] **範圍**：超出本 MR scope 的（既有架構債／其他 ticket）標「不阻擋 merge」或「建議獨立處理」。
   - [ ] **發現問題先說明再修正**，不要直接發布。

CRED=$(echo "url=${GITLAB_URL}" | git credential fill 2>/dev/null)

  # 還是沒 token：別靜默失敗，印出 body 讓使用者手動貼上發布

  python3 -c "print('''<review content>''')"
else

  python3 -c "
import json
body = '''<review content>'''
print(json.dumps({'body': body}))
" | curl -s --header "PRIVATE-TOKEN: $PASSWORD" \
    --header "Content-Type: application/json" \

    "${GITLAB_URL}/api/v4/projects/${GITLAB_PROJECT_ID}/merge_requests/<MR_ID>/notes"

## 注意事項

- **一張 MR 開一個新 session（token 衛生）**：別在單一 session 連續 review 多張 MR——cache_read 主要來自「單一 session 跨多天／多張 MR 不重開」，每輪重讀累積對話會隨 session 壽命線性膨脹（實測跨多天多張 MR 可滾到上億）。跨 MR 找關聯：**先查 MEMORY**（本就是為此存在，讓 fresh session 不重讀舊對話又記得結論）；只有 memory 沒記的細節才 **targeted grep 舊 session log**（`~/.claude/projects/<專案目錄>/<session-id>.jsonl`，usage 在 `message.usage`）——**只抽片段、絕不整段載入**。
