# 回頭整理教訓

**範圍：** "$ARGUMENTS"（空白就全看）

建議頻率：每個月一次，或累積 10 張 MR 一次。單一教訓當下就回饋，這裡處理的是「單看一張看不出是同一個毛病」的東西。多數教訓當下已經回饋過，第一次跑出來大部分落在「已寫進文件」是正常的。

讀的量大，建議交給一個子代理讀素材、歸類，主 session 只收結論。

## 1. 讀素材

1. **memory 位置**：以這個 session 開頭載入的 `MEMORY.md` 所在目錄為準。
2. **教訓**：用 grep 抽段落，不整檔讀：`grep -n -E '教訓|被 drop|待回饋|尚未動'`，再讀命中處前後幾行。另外讀所有 `type: feedback` 的檔案。
3. **plugin 文件**（比對用）：
   - `${CLAUDE_PLUGIN_ROOT}/commands/review-mr.md`
   - `${CLAUDE_PLUGIN_ROOT}/skills/principles/SKILL.md`
   - `${CLAUDE_PLUGIN_ROOT}/skills/code/SKILL.md`
   - `${CLAUDE_PLUGIN_ROOT}/rules/communication.md`
4. **舊對話**：只在某條教訓的來龍去脈講不清時，才對 memory 目錄旁的 `<session-id>.jsonl` 做 targeted grep，只抽片段。舊對話可能已被自動清掉，沒有就略過。

## 2. 歸類

把每條教訓歸成「同一種毛病」：看根因，不看發生在哪張 MR。單看一張不像、放在一起才看得出是同一類的，正是這一步要找的。每一類記下出現次數與各次出處。

## 3. 對照文件，分類

每一類先問：已經寫進文件了嗎？

- **已寫進文件**：列出對應的條目標題，不用動。
- **反覆出現（兩次以上）、文件沒寫**：提案新增。
- **紀錄裡寫了「待回饋」「尚未動」**：提案新增，這是當時想回饋卻沒做的。
- **反覆出現、但寫了也擋不住**：列出次數與試過的做法，不硬提新機制。先查 memory 有沒有「試過、不可行」的紀錄，有就照它。
- **只出現一次、也沒標待回饋**：留在 memory，等再出現。

每條「提案新增」都附上 review-mr「文件維護」段評估六問的答案（已涵蓋？放哪層？是不是可檢查的絆線？會不會跟別條打架？進文件還是 memory？值不值得版面？），使用者看到就能直接拍板。

另外列出：

- **過時內容**：memory 或文件裡指向舊位置、舊做法的描述。
- **重複**：同一條規則在 memory 與 plugin 文件各一份。建議哪邊留正本、哪邊改成一行指標。

## 4. 提案文字的規則

- **只用一般程式術語**：不出現專案裡真實的方法名、欄位名、模組名、內部自創詞、單號、人名。素材裡都是真實名稱，寫提案時一律改寫。
- **要跨專案通用**：plugin 是所有專案共用的。只在這個專案成立的教訓，提案留在 memory，不進 plugin。

## 5. 輸出與權限

照溝通規則寫：先一段白話講這一輪最值得注意的一件事，再依上面的分類列出，每條附出處。

- **plugin 文件：只提案，不改。** 使用者決定要改的，回到 plugin 的原始 repo 改，不要改 `${CLAUDE_PLUGIN_ROOT}` 的安裝快取。結構性的改動推上去前要做多模型對抗分析。
- **memory 的過時指向**：列出來，使用者確認後才改。
