# 寫程式

**任務：** "$ARGUMENTS"

開始前先用 Skill 工具載入 `alma:principles`，整個過程照它做。引用原則時用條目標題。

## Phase 1：需求

1. 有 Jira 單就讀本單、父單、前後子單，只抽「要做什麼」：目標、人做的決定、驗收條件、已接受的風險。
2. 寫一句目標（有幾個寫幾個）＋來源。使用者輸入的任務本身就是需求來源；只有任務描述模糊、或幾種讀法會做出不同東西時，才先問再往下。

## Phase 2：設計

只有新增元件、或改變某段流程的行為／順序（含並發、狀態轉換、排程互動）時才做這段；小修改直接跳 Phase 3。

1. grep 同類模組，找現成的做法和慣例（〈先找現成的〉）。
2. 改動的是一段流程就畫文字流程圖，含改前與改後、主要路徑、錯誤路徑。
3. 牽涉聚合狀態就先列推導表（〈狀態由別處推導時，先列推導表〉）。
4. 給使用者看目標、流程圖、做法，**等確認再寫**。

## Phase 3：實作

1. 做最小的改動。想加抽象、guard、try/except 時，先過〈只為真實的使用者抽象（YAGNI）〉〈修在產生錯誤狀態的地方〉。
2. 每條錯誤路徑寫完，問「這裡壞了誰會知道」（〈出事要看得到〉）。
3. 新增自動化機制時，列出它碰到的既有告警與流程（〈新增機制時，回頭查既有流程〉）。

## Phase 4：驗證

1. 從 Phase 1 的目標推測試，不照實作抄預期值（〈好的測試〉）。
2. 實際跑測試，貼出真實結果。失敗就照實說，不要寫「應該可以」。
3. 拿 `alma:principles` 每一條的「審」逐條對自己的 diff，每條寫一句看了什麼。
4. 交付：一句白話講做了什麼、怎麼驗證的、還有什麼沒做。不 commit、不 push，除非使用者要求。
